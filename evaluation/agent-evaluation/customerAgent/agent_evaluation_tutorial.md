# Agent 测评教程：从“能回答”到“可验证地完成任务”

本文面向第一次搭建 Agent 测评的开发者，以本项目的智能客服为例，讲清楚测什么、如何准备数据、如何评分、如何定位问题，以及怎样把测评接入迭代流程。

- 编写日期：2026-10-13。
- 配套文档：[customerAgent 测评方案](./customer_agent_evaluation_plan.md)。
- 本文是教学文档，示例数字是演算或建议，不是本项目已经测得的结果。
- 阅读顺序：先理解第 1～5 节，再实践第 12 节；需要计算指标时查第 6～8 节。

## 1. Agent 测评到底在测什么

普通问答测评经常只比较“问题”和“答案”。Agent 还会识别意图、读取上下文、调用工具、更新状态、决定追问或转人工。因此，测评对象应该是完整系统：

```text
用户输入 + 会话状态 + 身份权限 + 知识/业务数据
                    ↓
        识别 → 分解 → 补槽 → 路由 → 工具 → 回答
                    ↓
        最终结果 + 执行轨迹 + 状态变化 + 时间/成本
```

例如用户问：“订单 TR202610130001 到哪了？”系统回答“已经交付”，不能据此判定通过。还需要检查：

1. 这个订单是否属于当前用户可访问的范围。
2. 查询工具收到的是否确实是这个订单号。
3. 返回的交付状态是否来自本次工具结果。
4. 最终回答有没有把支付状态误说成交付状态。
5. 有没有泄露卡密、联系方式等不应返回的内容。
6. 是否在合理时间内完成，是否发生多余调用。

反过来，如果用户没提供订单号，正确地追问可能就是这一轮的成功结果。不能把“直接给答案”当成唯一成功标准。

### 1.1 三个必须同时看的维度

| 维度 | 核心问题 | 客服示例 |
|---|---|---|
| 结果 | 用户的目标是否达成 | 正确查询自己的订单；需要人工时成功建单 |
| 过程 | 系统是否按必要约束执行 | 身份由服务端确定；槽位没有串到另一个订单 |
| 代价 | 完成任务用了多少资源 | 多少轮追问、工具调用、模型 token、耗时 |

结果正确但越权，仍然失败；权限合规但始终答非所问，也失败。不能用一个加权总分让高文风分抵消越权。

### 1.2 测评不等于演示，也不等于单元测试

演示回答“这个例子能不能跑通”；单元测试回答“一个确定分支是否符合约定”；系统测评回答“在一组代表性场景中，这个版本有多可靠，哪里会失败”。它们相互补充。

一个很有用的区分是：**能力集**探索目前还不稳定的能力，**回归集**保护已经承诺的行为。这两类集合可以分开报告，不要因为难题多就掩盖回归，也不要只测容易题制造高分。[方法参考：Anthropic Agent 评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## 2. 先掌握七个概念

| 概念 | 含义 | 本项目例子 |
|---|---|---|
| Case / Scenario | 一个完整场景，包含前置数据与成功条件 | 缺订单号，追问后查到订单 |
| Turn | 场景中的一轮用户输入与系统响应 | 第二轮输入订单号 |
| Trial | 对同一场景的一次独立执行 | 新建会话重新跑一遍上述两轮 |
| Fixture | 固定的测试环境与数据 | 测试买家、订单、知识版本 |
| Oracle / Gold | 判断对错的独立依据 | 数据库业务事实、经审核规则、人工标注意图 |
| Trace / Trajectory | 可观察执行轨迹 | 识别来源、实例槽位、工具参数、响应、状态 |
| Grader / Harness | 评分器 / 执行与汇总框架 | JSON 断言 / 按数据集调用 API 并生成报告的程序 |

特别注意统计单位：一个三轮场景重复三次，是 **1 个 case、3 个 trial、9 个 turn**。不能把 9 轮都当成 9 个独立场景计算可靠性。

不需要收集模型隐藏思维过程。结构化决策、工具调用、证据、状态变化已经可以支持大部分评测与定位。

## 3. 从需求写出“可评分”的用例

### 3.1 不要只写一句问题和一段参考答案

不够好的用例：

```text
问题：我的订单什么时候结算？
答案：预计明天。
```

它缺少用户身份、订单号、当前时间、结算条件和依据。即使系统输出“明天”，也可能是猜的。

更好的用例应包含以下信息：

| 字段 | 要回答的问题 |
|---|---|
| 前置条件 | 谁在提问？哪些数据存在？当前时间是什么？ |
| 用户目标 | 用户最终想完成什么？ |
| 输入轮次 | 一次问完，还是需要补充信息？ |
| 预期事实 | 哪些值、关系和限制必须正确？ |
| 允许行为 | 可以追问吗？可以调用哪些工具？ |
| 禁止行为 | 不得访问谁的数据？不得承诺什么？ |
| 终止条件 | 怎样才算完成，最多允许几轮？ |
| 评分证据 | 从响应、工具记录还是数据库检查？ |

### 3.2 用“事实和约束”替代唯一措辞

以两个订单为例：

```text
前置：当前买家拥有 TR202610130001 和 TR202610130002。
输入：查一下这两个订单现在的交付状态。
预期：保留两个 ORDER_STATUS 实例，各自查询对应订单。
      两项结果都与测试快照一致，没有交叉引用。
禁止：按意图编码去重后只留下一个结果。
允许：先回答哪个订单都可以，文案不要求逐字相同。
```

业务事实和关系应严格评分；自然语言表达通常允许等价变化。否则一次正常改写就会导致“假回归”。

### 3.3 先约定预期结果类型

建议每个场景标一个主要结果：

- `ANSWER`：有充分信息，应完成查询或解释。
- `CLARIFY`：信息不足，应问清楚，不能猜。
- `HANDOFF`：明确请求人工或符合升级规则，应建立真实工单。
- `REFUSE`：越权或禁止操作，应阻止且不泄露事实。
- `FALLBACK`：依赖不可用或无可靠知识，应明确说明能力边界。

这些是**测评标签**，不一定是业务接口中的枚举。比如单轮 `CLARIFY` 合格，并不意味着多轮场景已完成；还要继续验证补充信息后能完成任务。

## 4. 分层测试：先定位，再整体评估

| 层次 | 固定什么、测什么 | 适合发现的问题 |
|---|---|---|
| 规则/单元 | 固定模型返回和工具结果，测一个函数或策略 | 阈值边界、参数校验、白名单 |
| 组件 | 单独测识别、检索、权限或输出保护 | 意图混淆、召回缺失、脱敏遗漏 |
| 编排集成 | 固定依赖，执行完整状态图 | 路由错、实例丢失、澄清串线 |
| API 端到端 | 真实 HTTP、身份、数据库和服务链路 | 鉴权、幂等、持久化、超时 |
| 真实模型端到端 | 加上真实分类、Embedding、知识工具调用 | 语义理解、模型格式与调用稳定性 |
| 用户体验/线上观测 | 前端交互和真实流量统计 | 重复提交、结果展示、实际解决率 |

顺序通常是：先让确定性契约通过，再评价真实语义能力。Mock 可以验证状态图能否正确处理一个结果，却不能证明真实模型能生成那个结果。

结果评分和轨迹评分也应分开：轨迹用来约束必须经过的权限检查、必要工具和参数关系，不必把所有合法路径锁成同一个字符串。LangChain 的官方示例也区分最终响应、中间步骤和不同粒度的轨迹评估。[参考：复杂 Agent 评测](https://docs.langchain.com/langsmith/evaluate-complex-agent)。

## 5. 怎样建立可靠的数据集

### 5.1 四种来源组合使用

1. **需求拆解**：每个意图、权限规则、状态转换至少有正例和反例。
2. **经脱敏的实际问题**：保留口语、错别字、省略、混合诉求；先人工确定 gold。
3. **历史失败**：把线上问题缩成可复现用例，进入长期回归集。
4. **有目的的合成**：针对少见边界和攻击生成候选，再人工审核。

生成模型可以扩充表述，但不能自己生成事实再自己证明事实。订单事实应来自独立 fixture，平台规则应来自已审核文档。

### 5.2 至少覆盖这些维度

| 维度 | 示例 |
|---|---|
| 表达 | 标准语、口语、中英文、全角字符、错别字 |
| 信息量 | 信息齐全、缺订单号、两个可能指代对象 |
| 结构 | 单意图、不同意图、同意图不同订单 |
| 轮次 | 初次提问、补槽、改口、切换主题、连续无效回复 |
| 身份 | 买家、卖家、无关用户、管理员、未登录 |
| 知识 | 有答案、无答案、旧版本、内部文档、冲突规则 |
| 依赖 | 正常、超时、空结果、非法模型输出、服务不可用 |
| 对抗 | 用户注入、检索文档注入、伪造工具参数、越权诱导 |

覆盖不是全排列。先保证高影响路径和已知边界，再根据失败分布补充组合。

### 5.3 开发集与保留集分开

- 开发集用于修改 prompt、选择阈值、完善工具策略。
- 保留集用于评价候选版本，不能每次看完失败就继续在同一批题上调参并宣称泛化提升。
- 按**语义模板族/完整会话**划分，而不是随机拆散同一句话的同义改写。
- 意图检索示例、few-shot 示例和评测问句要查重；还要人工检查语义近重复。
- 每份数据记录版本与 hash，记录每次修改的原因。

如果开发集全是“订单在哪”，保留集全是“我的订单在哪”，两个集合名字不同也无法避免泄漏。平台规则是允许被检索的证据；问题模板、标准回答和隐藏评分条件则不能直接投喂给被测系统。

### 5.4 人工标注也需要规则

两名标注者先独立标同一批题，讨论意图、槽位与升级边界的分歧，形成标注手册。无法达成一致的题进入争议集，暂不进入自动发布门禁。不要让含糊 gold 变成开发者必须迎合的错误答案。

## 6. 如何选择评分器

### 6.1 确定性评分：能用代码验证的先用代码

适合校验：

- JSON 结构、枚举和必填字段。
- 工具名、调用次数、订单号、权限身份。
- 事实值、引用文档版本、工单是否存在。
- 禁止字段是否出现在嵌套对象、日志或响应中。
- 幂等重放是否复用同一个 run，业务表是否被意外修改。

简单伪代码如下；这里的 `trace` 是测评程序归一化后的数据结构，不是现有接口定义：

```python
def grade_order_case(expected, actual, trace):
    checks = {
        "correct_order": actual["order_no"] == expected["order_no"],
        "correct_delivery": actual["delivery_status"] == expected["delivery_status"],
        "actor_from_server": trace["actor_id"] == expected["actor_id"],
        "no_forbidden_fields": not trace["forbidden_field_hits"],
    }
    return {"passed": all(checks.values()), "checks": checks}
```

不能直接从响应复制一个值，填回 `expected`，再比较二者。那只是证明数据被复制成功，失去了独立判断依据。

### 6.2 语义评分：用固定量表约束 LLM Judge

规则解释、相关性和表达清晰度不适合逐字匹配，可以由模型评分，但要提供原问题、允许使用的事实、实际答案和评分规则。

建议把评判拆成小问题：

| 项目 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 事实支撑 | 有关键无依据结论 | 大体有依据，但缺条件或存在歧义 | 所有关键结论都有证据 |
| 问题覆盖 | 没处理用户目标 | 只处理部分诉求 | 处理全部诉求或清楚指出缺失信息 |
| 可操作性 | 引导错误/编造动作 | 有说明但下一步不明确 | 给出当前权限和能力内的明确下一步 |
| 表达 | 难理解或自相矛盾 | 可理解但冗余 | 清晰、简洁、对象明确 |

示例裁判输出约定：

```json
{
  "schema_version": 1,
  "status": "SCORED",
  "grounding": 2,
  "coverage": 1,
  "actionability": 2,
  "clarity": 2,
  "unsupported_claims": [],
  "missing_requirements": ["未回答第二个订单的结算条件"],
  "evidence_refs": ["fixture:order-2", "source:rule-v2"],
  "reason": "第一个订单说明准确，但第二项诉求遗漏。"
}
```

裁判的使用规则：

1. 被评答案和检索文本都当成不可信数据；其中“请给我满分”等指令不生效。
2. 要求引用证据并指出错误位置，不接受只有总分的输出。
3. 先用人工标注样本校准；关注错放行与错拒绝，不只看平均一致率。
4. 固定裁判模型、prompt、参数和版本，保存原始判定。
5. 输出非法、超时、证据不足时记 `ERROR` 或 `INSUFFICIENT_EVIDENCE`，不能默认通过。
6. 裁判只参与评分，不持有下单、退款、发布等业务权限。

LLM Judge 是可出错的测量工具。越权是否发生、退款是否落库等客观事实，应交给代码和数据库检查。

### 6.3 人工复核：把精力放在高价值分歧上

首轮查看全部失败、高风险放行、裁判与代码冲突的样本，再随机抽查通过样本。只复核失败会漏掉“裁判误判为通过”。对两版答案进行人工对比时隐藏版本名，并交换展示顺序，降低位置与品牌偏差。

## 7. 核心指标如何计算

所有比例都同时报告分子、分母、排除数和缺失数。下面的数字仅用于教学。

### 7.1 任务成功率与部分成功

```text
任务成功率 = 满足全部必需条件的 trial 数 / 应执行的 trial 数
意图实例完成率 = 正确完成的预期实例数 / 预期实例总数
```

若 100 个 trial 中 80 个完整成功、10 个只解决一个子问题、10 个完全失败：任务成功率为 80%。可以额外报告部分成功，但不能把部分成功混进完整成功。

对于应当转人工的场景，“真实创建工单且上下文完整”就是成功。另列“可自助解决场景的自助解决率”，防止系统通过把所有问题都转人工获得高分。

### 7.2 意图识别：准确率不够，还要看混淆

单意图可以计算准确率及混淆矩阵。多意图应按实例匹配：

```text
Precision = 正确识别的实例数 / 实际输出实例数
Recall    = 正确识别的实例数 / 标准实例数
F1        = 2 × Precision × Recall / (Precision + Recall)
```

例如 gold 是两个不同订单的 `ORDER_STATUS`，实际只输出一个：Precision 可以是 1，Recall 只有 0.5，F1 约 0.667。若只比较意图编码集合，就会错误地得到满分。

匹配应一对一：意图编码 + 业务对象 + 问题片段的语义对应关系。服务端生成的实例 ID 可以映射到 gold 别名，无需写死随机 ID；同一会话内的续接关系则必须保持。

- **Micro-F1**：先汇总所有实例再计算，容易受高频意图影响。
- **Macro-F1**：各类分别计算再平均，更能暴露少数类问题。
- 无预测/无 gold 的场景预先定义约定；不适用的指标记 N/A，不凭空赋满分。

区分模型原始分类和策略处理后的路由。例如低置信度被系统改成 `OTHER`，这是路由结果；如果没有保存原始分类，就不能宣称已经测到了纯模型分类准确率。

### 7.3 槽位与多轮状态

至少记录：

- 槽位值准确率：已给出的订单号/售后单号是否提取正确。
- 完整实例准确率：同一个实例的意图和全部必需槽位都正确。
- 串槽次数：甲订单的号是否被用于乙实例；这是高风险错误，单列。
- 澄清成功率：补充有效信息后，是否完成原任务。
- 不必要澄清率：信息已经充分，却又追问的比例。
- 重复执行次数：已完成实例是否在后续轮次被无理由重查。

第一轮没订单号时，不抽取任何订单号通常是正确行为。槽位缺失和槽位错误必须区分。

### 7.4 工具执行

不能只计算“调用工具返回 HTTP 200”。工具测评应包含：选择正确、参数正确、身份正确、次数合理、结果被正确使用。

硬性检查包括禁止工具调用次数为 0、无权限事实泄露次数为 0。效率项如多余只读调用可以另列；一个工具服务不可用不应被归为模型识别失败。

### 7.5 知识检索、引用与事实支撑

这三个问题各不相同：

1. **检索召回**：所需文档是否被找到？可用 Hit@K、MRR、参考证据覆盖率。
2. **引用有效性**：引用的文档、版本、片段是否真实存在且允许公开？
3. **结论受支持**：该片段是否真正支持回答中的结论和适用条件？

```text
Hit@K = Top K 中至少出现一个相关文档的查询数 / 查询数
MRR = 所有查询的首个相关结果排名倒数之和 / 查询数
      （完全未命中记 0）
```

如果回答“所有订单 24 小时内结算”，却引用了“确认交付后满足条件的订单可结算”，引用虽然存在，结论依然不受支持。

RAGAS 的 Faithfulness 关注答案中的陈述是否能由提供的上下文支持；它不能单独证明上下文是最新、权威、可公开的，也不能证明用户的全部问题已回答。[参考：RAGAS Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)。

订单实时状态应对照业务工具事实；规则性结论应对照知识证据，不能用知识文档替代当前订单事实。拒绝回答或无知识场景不要为了获得高引用率而添加无关引用。

### 7.6 人工升级与安全

```text
升级 Precision = 应升级且实际升级数 / 实际升级数
升级 Recall    = 应升级且实际升级数 / 应升级数
误升级率       = 不应升级却升级数 / 不应升级数
```

人工请求漏转、风险漏转、普通问题误转分别统计。无必要地转人工会增加运营负担；高风险未升级可能更严重，不能用平均值抵消。

安全指标建议用“失败次数 + 攻击场景数 + 具体失败类型”表达，包括越权泄露、伪造身份、执行禁止动作和敏感输出。测试 30 次没有泄露，只能证明这 30 次未观察到问题，不能宣称系统绝对安全。

### 7.7 时间、成本与覆盖率

- 延迟报告 P50/P95/P99、样本数、超时率，并区分单意图、多意图、多轮总时长。
- 同时记录客户端端到端耗时与服务内部耗时；它们包含的排队、鉴权、落库时间不同。
- 失败和超时不能从性能报告删除。若分位数仅对成功请求计算，必须明确标注，并单列全部请求分布和超时数。
- 成本分别记录 Chat、Embedding、评分模型和基础设施口径；价格来源与生效日期单独冻结。
- 每成功场景成本 = 全部被测执行成本 / 成功场景数，包含失败与重试成本；成功数为 0 时记不可计算。
- token 未提供是未知，不是 0；评测裁判成本不要混入 Agent 自身成本。

```text
评分覆盖率 = 得到有效评分的适用样本数 / 应评分的适用样本数
```

例如 100 条中只评出 10 条且全部高分，不能按“100% 通过”发布。实际执行缺失也要报告：服务不可用导致的未执行，与已执行且业务失败不是同一原因，但都不能支持通过结论。

## 8. 多跑几次，怎样避免“挑一次最好结果”

同一模型和 prompt 也可能产生波动。温度为 0、固定 seed 都不等于整个分布式系统绝对确定。

对每个场景独立执行 k 次：

- **至少一次成功比例**：有一次成功就计入，衡量重试潜力；本教程称 observed pass@k。
- **全部 k 次成功比例**：k 次都成功才计入，衡量稳定性；本教程称 observed all-pass@k，常见资料也称 pass^k。
- **平均单次成功率**：成功 trial 数 / 全部 trial 数。

假设单次成功概率为 p，各次独立且分布相同，理论上至少一次成功为 `1-(1-p)^k`，全部成功为 `p^k`。例如 p=0.8、k=3，分别是 99.2% 和 51.2%。这是概率演算，不能把一次实验的 p 直接当成真实概率。

有些基准用组合估计器定义 pass@k。报告中应明确采用上面的实测比例还是其他估计器，不能把不同定义混着比较。

独立执行需要新会话、新消息标识、可重复的 fixture，并隔离上一次修改的状态。重复同一个幂等键得到同一个缓存结果，并不是可靠性复测。

### 8.1 样本量与不确定性

20 条全通过和 2,000 条全通过提供的证据强度不同。报告给出样本量与置信区间；A/B 比较按同一场景配对，多轮或重复试验可按场景聚类 bootstrap，避免把相关轮次当成独立样本。

一个常用的粗略直觉是：若 n 次相互独立、同分布的二项试验观察到 0 次失败，95% 单侧失败率上界约为 `3/n`（n 足够大时）。100 次零失败，上界仍约 3%；真实客服流量不一定满足独立同分布，不能把这个估计当成安全保证。

小样本某类只多对一题，可能产生很大的百分比变化。先查看成对胜负和具体案例，再决定是否需要扩大样本。

## 9. 多轮评测怎样设计

优先从固定脚本开始，只有需要探索开放对话时再引入用户模拟模型。

```text
第 1 轮：查订单 TR202610130001 的交付，再查另一笔的结算。
预期：交付完成；结算缺订单号，追问；保存两项各自状态。
第 2 轮：TR202610130002。
预期：只补结算实例；不重做第一项；使用第二笔订单事实。
```

每轮既检查输出，也检查下一轮将读取的状态。否则回答看起来正确，但系统已经把错误订单写入上下文，问题会在第三轮才出现。

如果使用用户模拟器：

1. 把用户目标和私有事实与 Agent 可见信息分开。
2. 模拟器只在被问到时补充信息，不能偷偷替 Agent 完成任务。
3. 明确最大轮数与结束条件，防止无限对话。
4. 记录模拟器版本，抽查它有没有偏离脚本目标。
5. 开放模拟结果与固定脚本回归结果分开报告。

## 10. 怎样分析失败

按**第一个有证据的错误环节**归因，而不是所有失败都写“模型不够好”：

| 类型 | 观察到的证据 | 优先检查 |
|---|---|---|
| 数据/标注错误 | gold 与权威规则冲突 | 标注手册、fixture 版本 |
| 识别错误 | 单据查询被判成一般规则 | 意图边界、负例、prompt |
| 补槽错误 | 两个实例用了同一个订单号 | 实例绑定、指代和上下文规则 |
| 路由/策略错误 | 识别正确却进入错误分支 | Graph 条件边、置信度策略 |
| 检索错误 | 相关文档不在候选中 | 版本过滤、Embedding、召回参数 |
| 工具/权限错误 | 参数正确却越权返回 | 服务端 actor 与所有权校验 |
| 回答错误 | 工具事实正确，输出结论错误 | 事实映射、输出拼装、保护逻辑 |
| 运行时错误 | 正确路径因超时中止 | 预算、依赖、取消与资源释放 |
| 评分器错误 | 裁判无视证据或不能解析 | rubric、解析、覆盖率与复核 |

可以通过受控替换帮助定位：把识别结果替换为 gold，看后续能否通过；把检索内容替换为正确证据，看回答是否改善。这样的诊断试验必须单独标记，不能冒充原系统端到端成绩。

修复时尽量只改变一个主要变量，再跑原失败用例和相关回归。不要同时换模型、改 prompt、改阈值和改文档后再猜是哪一项有效。

## 11. 如何比较两个版本并设置门禁

### 11.1 固定实验条件

冻结代码版本、prompt、模型标识与参数、知识版本、意图库发布版本、fixture、用例 hash、裁判版本、超时和并发。记录实验时间及供应商返回的实际模型标识；如果供应商不提供更细的快照信息，就明确这种复现限制。

候选版和基线跑同一批场景，尽量交错执行，降低时间段负载差异。展示：共同成功、共同失败、基线成功/候选失败、基线失败/候选成功，并复核退步样本。

### 11.2 门禁分层

1. **硬性契约**：越权、禁止写操作、串槽、伪造证据等出现一次就阻断。
2. **质量要求**：任务成功率、分类召回、澄清与升级质量达到事先约定的门槛。
3. **运行要求**：性能、超时率、成本和评分覆盖率符合预算。

具体门槛由业务风险与首轮基线校准，不存在适合所有 Agent 的统一“优秀分数”。门禁在看候选结果前冻结，不能测完再调到刚好通过。

### 11.3 线上观测是补充证据

投诉率、转人工率、再次询问率、用户反馈有价值，但受问题难度、用户期待和流量结构影响。满意度高不必然代表事实正确，满意度低也不必然是 Agent 错误。

先用离线测试建立最低保证，再用受控灰度和线上抽检验证流量代表性。线上失败经脱敏和人工复核后回流成新回归用例。

## 12. 从零开始的练习路线

### 练习一：手工建立 12 个场景

各写 2 个：订单查询、缺槽澄清、多意图、规则引用、转人工、权限攻击。每个场景补全身份、fixture、允许行为和禁止行为。

交付物：用例表和 gold。自检：另一位开发者不询问你，能否根据这些信息判断通过或失败？

### 练习二：采集真实结果

使用测试用户创建会话，提交消息；按返回的 runNo 获取管理员轨迹。保存原始响应，再生成归一化副本；不要覆盖原始记录。

交付物：每个 trial 的输入、输出、实例槽位、工具调用、证据、耗时。暂时没有某项观测能力时注明缺失，不补写猜测值。

### 练习三：先写 5 类确定性断言

检查结构、实例完整性、工具参数、权限边界、引用有效性。对每条断言故意构造一个错误输入，确认评分器能拒绝。

交付物：逐项 `PASS/FAIL/NOT_EVALUATED`，以及指向原始证据的位置。评分器自己也需要验证，尤其要防止“缺字段被默认成通过”。

### 练习四：加入语义裁判和人工校准

挑选有争议的规则解释题，按第 6 节量表人工评分，再让裁判评分。记录分歧，调整评分规则，而不是修改 gold 迎合裁判。

交付物：人工与模型的对照表、错放行案例、裁判版本。

### 练习五：重复运行并做一次版本对比

同一场景独立跑 3 次，再只改一个因素，例如识别 prompt。比较平均成功率、all-pass@3、退步案例和成本。保证不是使用相同幂等键重放。

交付物：可复现的基线报告。再按配套方案扩充场景和接入 CI。

## 13. 本项目最容易误判的地方

| 容易误判 | 正确做法 |
|---|---|
| HTTP 200 或 run 为 SUCCEEDED 就算通过 | 检查 errorCode、各 intentResults、事实与整体目标 |
| Mock 跑通即说明模型理解准确 | Mock 只验证契约，真实模型另测 |
| L3_LLM 来源就证明发生了模型调用 | 同时看 provider 和实际模型调用探针 |
| 意图编码集合相等就算多意图正确 | 一对一匹配意图实例及各自业务对象 |
| 引用非空就说明答案可靠 | 校验版本、权限、实例归属和结论支撑 |
| 转人工文案存在就算完成 | 检查真实工单、幂等性和上下文 |
| RAG 脚本生成的答案就是客服答案 | 评分真实客服 API 的 answer 和 intentResults |
| 未提供 token 记成 0 成本 | 报告未知和计量覆盖率 |
| 评分失败的样本直接删除 | 保留缺失状态，检查覆盖率门禁 |
| 同一个请求重试三次就是稳定性验证 | 重放验证幂等；新会话独立执行验证稳定性 |

对应的目录、接口、数据集结构和验收门槛见 [customerAgent 测评方案](./customer_agent_evaluation_plan.md)。
