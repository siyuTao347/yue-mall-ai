# 阶段一与阶段二优化评审

| 属性 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 日期 | 2026-09-30 |
| 状态 | 待评审 |
| 评审范围 | 阶段一担保交易闭环、阶段二风控体系、网关接入后的整体链路、前端交易工作台 |
| 评审方式 | 静态代码评审 + 既有设计文档比对 |
| 结论 | 主体业务闭环已经成型，但支付回调安全、跨服务一致性、查询与风控性能、前端操作闭环仍有明显优化空间 |

本文只提出优化建议和验收标准，不直接修改业务代码。

## 一、总体结论

阶段一已经覆盖了商品发布、卡密导入、下单支付、托管、交付、确认、结算、售后仲裁和提现等主流程；阶段二也已经具备事件采集、规则评估、案件处置、命令下发和关系图谱能力。整体设计方向是对的，测试也覆盖了较多核心分支。

当前最需要优先处理的是四类问题：

1. **支付回调签名可伪造**：现有签名材料全部可由外部推导，缺少服务端密钥、时间戳和 nonce，属于资金安全风险。
2. **跨服务事务偏重**：订单本地事务中包含资产、风控、资金等远程调用，一旦出现本地回滚而远程已提交，目前主要依赖人工或既有补偿逻辑，缺少统一恢复机制。
3. **查询与风控性能边界不清**：多个列表固定 `LIMIT 100` 且无分页，风控评估每次实时扫描事件表，数据量增长后容易放大数据库压力。
4. **前端闭环不完整**：加载、错误、并发操作、状态文案、证据展示、风控案件工作台等体验缺口较多，阶段二能力尚未形成完整运营入口。

建议按“先安全与一致性，再性能与操作闭环，最后工程规范”的顺序推进。

## 二、优先级定义

| 优先级 | 定义 | 建议处理窗口 |
| --- | --- | --- |
| P0 | 影响资金安全、数据正确性或可被直接利用的安全问题 | 立即处理 |
| P1 | 影响性能、稳定性、运营效率或关键用户路径的问题 | 近期版本处理 |
| P2 | 影响可维护性、细节体验或长期演进的问题 | 排期处理 |

## 四、P0：支付回调安全

### SEC-001 Mock 支付回调签名可伪造

**现状**

- `TradeOrderService.buildPayment()` 使用 `sha256(orderNo + orderAmount)` 生成 `callbackTokenHash`。
- `verifyCallback()` 校验 `sha256(paymentNo + "|" + amount + "|" + callbackTokenHash)`。
- `paymentNo` 是 `"PAY" + orderNo`，金额来自公开订单信息。
- 因此签名所需的全部材料都可以由外部推导，没有服务端随机密钥参与。
- 回调签名没有时间戳和 nonce；`callbackNo` 唯一只能防止同一个回调号重复，不能防止换号重放。
- 网关配置中 `POST:/api/payment/callback` 是公开路径。

**影响**

攻击者只要知道订单号和金额，就可以构造签名并发起成功回调，导致未支付订单被标记为支付成功，进而触发资金托管和资产交付。该问题属于资金安全级风险，不能只当作 Mock 演示问题处理。

**建议方案**

1. 引入服务端回调密钥，签名算法改为 HMAC，例如：
   - `HMAC-SHA256(callbackSecret, paymentNo + "|" + orderNo + "|" + amount + "|" + timestamp + "|" + nonce)`
   - 密钥仅保存在配置中心或密钥管理系统，不能出现在前端或公开接口响应中。
2. 回调报文增加 `timestamp` 和 `nonce`：
   - 时间戳超过窗口直接拒绝。
   - nonce 在窗口内唯一，使用数据库唯一键或 Redis TTL 去重。
3. 明确回调来源控制：
   - 生产环境只允许支付渠道回调来源访问。
   - 网关层和服务层同时校验来源与签名，避免服务直连绕过。
4. 对签名失败、时间戳越界、nonce 重复建立计数告警，异常升高时触发风控事件。
5. Mock 支付能力通过 profile 或环境开关隔离，生产环境默认关闭。

**验收标准**

- 未知密钥、错误金额、错误订单号、错误支付单号的签名均被拒绝。
- 相同 nonce 的重放请求被拒绝，不同 nonce 但超出时间窗口的请求也被拒绝。
- 成功回调只能推进一次支付状态。
- 签名失败、nonce 冲突和时间异常均有结构化日志与告警。
- 单元测试覆盖伪造签名、重放、并发回调和重复回调。

## 五、P0：跨服务一致性与事务编排

### TXN-001 本地事务内远程编排偏重

**现状**

`TradeOrderService` 中多个 `@Transactional` 方法直接调用远程或跨模块服务：

- `create()`：资产预留、风控评估、订单落库、支付单落库、事务后确认。
- `handleCallback()`：支付回调处理、资金冻结、资产确认等操作在同一条链路内执行。
- `settle()`：本地结算单与资金服务结算交织。
- `arbitrate()`：退款、资产作废、订单状态、商家统计在同一个事务方法内编排。
- `deliver()`：交付后同步记录风控事件。

**影响**

远程调用会拉长本地事务持锁时间，增加数据库连接占用和死锁概率。更关键的是，跨服务没有共享事务：远程操作成功而本地事务回滚时，会产生部分成功状态。当前代码里已有部分幂等和补偿设计，但缺少统一的恢复模型，后续排障成本会持续上升。

**建议方案**

短期先做三件事：

1. 明确每个跨服务操作的成功、失败、超时、重复四类结果，并为每类结果定义状态机去向。
2. 在发起远程资金或资产操作前先落“操作意图”，记录幂等键、目标状态和重试信息。
3. 将远程调用尽量移出数据库事务，避免本地长事务包住远程网络调用。

中期建议演进为 Saga 或本地消息/outbox 模型：

- 订单状态机只负责本地状态。
- 资金冻结、资产确认、结算、退款、商家统计等通过领域事件驱动。
- 每个消费方以业务单号或事件号做幂等。
- 为每个操作定义补偿动作和最大重试次数。
- 增加统一对账任务，扫描长时间停留在中间态的订单、结算单和资金流水。

同时建议拆分 `TradeOrderService`。当前该类承担创建、支付、交付、确认、结算、售后、仲裁、查询、状态流转等多个职责，继续叠加会降低可测试性。可按职责拆为：

- `TradeOrderCommandService`
- `PaymentCallbackOrchestrator`
- `DeliveryService`
- `SettlementService`
- `DisputeArbitrationService`
- `TradeOrderQueryService`
- `TradeOrderPolicy`
- `BusinessNoGenerator`

**验收标准**

- 每个跨服务操作都有明确的幂等键和补偿动作。
- 远程调用不再被本地数据库事务长期包裹。
- 人为模拟“远程成功、本地回滚”后，恢复任务能将业务推进到一致状态或进入人工处理队列。
- 订单、支付、资产、资金流水之间的对账差异可以自动发现。
- 并发创建、并发回调、并发结算、并发仲裁测试通过。

## 六、P1：查询能力与接口契约

### QUERY-001 核心列表缺少分页和筛选

**现状**

- `TradeOrderService.listByUser()` 固定 `LIMIT 100`。
- `FundService.getFlows()` 固定 `LIMIT 100`。
- `AssetListingService.listBySeller()`、`listPending()` 直接返回列表。
- `MerchantService.listByStatus()`、`WithdrawService.listByUser()`、`listPending()` 无分页。
- `RiskCommandService.listCases()` 有 page/size，但未返回 total，前端无法做完整分页。

**影响**

数据量增长后，用户看不到第 101 条之后的数据；管理端也无法按状态、时间、关键字定位问题。固定 `LIMIT 100` 还容易掩盖慢查询风险。

**建议方案**

1. 统一分页响应结构：
   - `list`
   - `page`
   - `pageSize`
   - `total`
   - `hasMore`
2. 用户侧订单、资金流水、商品列表、提现记录支持分页。
3. 管理侧统一支持状态、时间范围、关键字、商家 ID、用户 ID 筛选。
4. 对高频大列表使用 keyset pagination，避免深分页 `OFFSET` 扫描。
5. 为列表定义响应 DTO，避免直接暴露内部字段、大字段和 `detailHtml`。
6. 建立分页参数上限，例如默认 20，最大 100。

**验收标准**

- 所有列表接口返回 total 或游标。
- 常用筛选条件均能命中索引。
- 大数据量下第 N 页查询性能有基准数据。
- 前端可以翻页、筛选、刷新并保留当前查询条件。

### API-001 Controller 入参、校验与错误契约不足

**现状**

多个 Controller 直接接收 `Map<String, Object>`，再手动取值和转换类型；缺少统一的 Bean Validation。异常处理普遍 `catch (Exception e)` 后返回 `e.getMessage()`，业务错误多为 HTTP 200。`AuditLogTestController` 暴露测试和 benchmark 接口，虽然网关限制了 `/api/audit/**`，但服务直连场景仍缺少本地防护。

**影响**

参数类型错误、空值、超长字符串和非法数字容易进入服务层；错误响应不稳定，可能泄露内部实现；前端难以建立统一错误处理；HTTP 语义与响应体语义不一致。

**建议方案**

1. 为每个接口定义 Request DTO / Response DTO。
2. 使用 `jakarta.validation` 注解做入参校验。
3. 引入统一 `@RestControllerAdvice`：
   - 参数校验错误返回 400。
   - 认证授权错误返回 401/403。
   - 业务冲突返回 409 或稳定业务码。
   - 系统错误返回 500，不暴露堆栈和 SQL。
4. 建立全局错误码、traceId 和结构化日志。
5. 测试和 benchmark 接口通过 profile 或测试装配暴露，生产默认不可访问。

**验收标准**

- 不再使用 `Map<String, Object>` 作为核心接口入参。
- 参数校验测试覆盖空值、类型错误、边界值和超长输入。
- 错误响应包含稳定 code、message、traceId。
- 生产环境无法访问测试和 benchmark 接口。

## 七、P1：数据库与性能

### PERF-001 卡密导入与库存锁定存在循环单条操作

**现状**

- `AssetListingService.importCards()` 在循环中逐条插入 `CardSecret`。
- `AssetService.reserve()` 先查询卡密，再循环调用 `lockById()`。

**影响**

导入 1000 张卡密会产生 1000 次插入；高并发下单时，锁定卡密也会产生多次单条 UPDATE。数据库往返次数会随数据量和并发线性放大。

**建议方案**

1. 卡密导入改为批量插入，同时保留现有去重和 hash 冲突校验。
2. 卡密锁定改为按 ID 集合批量更新，并校验影响行数。
3. 评估一次性原子锁定 SQL，保证库存扣减和卡密占用在同一语句或同一事务内完成。
4. 并发更新保持确定性的排序或行锁策略，降低死锁概率。
5. 增加批量大小上限和失败分片策略，避免超大事务。

**验收标准**

- 导入和锁定不再存在逐条数据库往返。
- 并发下单不会超卖、重复锁定或漏锁定。
- 批量导入有性能基准和上限控制。
- 死锁与重试测试通过。

### RISK-001 风控指标实时扫描事件表

**现状**

`RiskMetricService.calculate()` 每次评估都会实时查询多个指标：

- 用户订单数、完成数、争议数、设备数、IP 数。
- 商家完成数、退款数、争议数、提现金额、提现账号关联数。
- 关联关系计算还会查询设备和 IP 表。

阶段二 Schema 中已经设计了 `t_risk_indicator` 物化表，但当前实现没有使用。

**影响**

一次风控评估可能触发十几次甚至更多数据库查询，且多个查询会扫描窗口数据。风控流量上升后，事件表会成为热点，评估延迟也会影响下单链路。

**建议方案**

1. 落地 `t_risk_indicator`：
   - 按用户、商家、设备、IP 维度物化窗口指标。
   - 通过事件驱动增量更新。
   - 明确指标新鲜度要求。
2. 对短窗口指标使用 Redis 或本地短 TTL 缓存，但要定义缓存击穿和降级策略。
3. 为每次评估设定数据库查询预算，例如固定上限，超过预算直接告警。
4. 对不需要强实时的指标改为异步预计算。
5. 将指标快照和规则版本写入决策证据，便于后续审计和回放。

**验收标准**

- 单次评估的数据库查询次数有固定上限。
- 事件表增长后评估耗时不会线性恶化。
- 指标物化任务可重放、可幂等。
- 指标快照与决策结果可追溯。

### RISK-002 规则缓存多实例一致性不足

**现状**

`RiskRuleCache` 是实例内 30 秒懒刷新；刷新没有同步控制，可能并发重复加载；`evict()` 只影响当前实例，多实例下规则生效时间不一致。

**影响**

规则变更后不同实例可能使用不同规则版本，导致同类请求出现不同决策。并发刷新还会造成数据库瞬时压力。

**建议方案**

1. 为规则表增加版本号或 updated_time。
2. 通过 Redis pub/sub、Nacos 配置事件或版本号轮询广播刷新。
3. 刷新时使用单线程或分布式锁，避免重复加载。
4. 决策证据记录规则版本。
5. 规则回滚支持灰度和快速失效。

**验收标准**

- 规则变更后所有实例在设定延迟内一致。
- 并发评估时不会触发重复刷新风暴。
- 每条决策都能追溯到当时的规则版本。

### RISK-003 关系图谱查询存在 N+1

**现状**

`RiskIdentityService.getRelations()` 按节点逐个查询 `t_relation_edge`。depth 最大为 2，节点上限 100，但查询次数仍可能随 frontier 放大。

**影响**

关联节点较多时，一次图谱查询会变成大量数据库往返，容易拖慢风控后台和评估链路。

**建议方案**

1. 对同一层 frontier 使用 `IN` 批量查询边。
2. 限制每层查询规模并保留 truncated 标识。
3. 如果图分析需求继续增加，再评估预构图或图数据库方案。
4. `buyerSellerRelation()` 可以改为精确 `exists` 查询，避免先取列表再内存判断。

**验收标准**

- 图谱查询次数与层级相关，不再与节点数线性相关。
- 深度 2、节点 100 的查询有性能基准。
- 图谱截断时前端能明确提示结果不完整。

## 八、P1：风控命令与维护任务

### CMD-001 命令补偿与多实例竞争不足

**现状**

`RiskCommandService` 已经使用事务提交后发送 MQ，并具备死信和人工重发；但缺少自动扫描未确认命令的任务。`RiskMaintenanceJob` 每分钟失效 PRECHECK，多实例同时执行时没有分布式锁或分片。

**影响**

MQ 消息丢失、消费失败或状态未回写时，命令会长期停留在中间态；多实例维护任务同时执行会重复扫描并产生无意义竞争。

**建议方案**

1. 增加命令超时扫描任务：
   - 超过阈值的 SENT 命令自动重试。
   - 超过最大重试次数后转为待人工处理。
   - 重试前先查询下游幂等状态。
2. 维护任务使用分布式锁或数据库抢占更新。
3. 明确命令状态机：`SENT`、`SUCCESS`、`FAILED`、`COMMAND_FAILED`、`TIMEOUT`、`MANUAL_PENDING`。
4. 为消费端补充幂等测试和重复消息测试。
5. 建立命令执行时长和失败率监控。

**验收标准**

- 模拟 MQ 丢消息或消费超时后，命令能自动恢复或进入人工队列。
- 多实例同时运行维护任务时，同一命令只被处理一次。
- 幂等消费测试和重试上限测试通过。

## 九、P1：资金账户与读操作边界

### FUND-001 读接口隐式创建账户

**现状**

`FundService.getAccount()` 查询不到账户时直接插入新账户。并发首次访问时可能同时插入并触发唯一键冲突，当前没有捕获处理。

**影响**

读接口隐含写操作，既影响性能，也带来并发异常。异常信息还可能透出到用户侧。

**建议方案**

1. 将账户初始化前移到注册、商家创建或首次资金操作流程。
2. 读接口查询不到账户时返回零余额视图，不直接写库。
3. 必须初始化时使用幂等 upsert，或捕获唯一键冲突后重查。
4. 明确账户创建的审计事件。

**验收标准**

- 并发首次查询不会抛出唯一键冲突。
- 查询接口不产生隐式写事务。
- 账户初始化有明确审计记录。

## 十、P1：前端体验与操作闭环

### FE-001 加载、错误、并发操作和请求控制不完整

**现状**

- `TradeWorkbench` 没有初始 loading 或 skeleton。
- `loadTradeData()` 中多个刷新失败被静默吞掉。
- `busy` 是单个字符串，只能禁用当前按钮，不同实体的操作仍可并发触发。
- 请求层缺少统一超时、取消和重试策略。

**影响**

接口失败时用户可能看到空列表却不知道是错误；同一订单、同一售后或同一提现可能被重复提交；页面切换后旧请求还可能覆盖新数据。

**建议方案**

1. 为每块列表建立独立 loading、error、empty、success 状态。
2. 刷新失败时展示错误条和重试按钮，不要静默替换为空数组。
3. `busy` 从单个字符串改为操作集合或 Map，支持：
   - 同一实体同一操作禁止重复提交。
   - 同一实体的互斥操作整体禁用。
   - 全局刷新时展示统一进度。
4. 请求层设置默认超时、AbortController 和统一错误解析。
5. 组件卸载或查询条件变化时取消过期请求。

**验收标准**

- 初始加载有明确反馈。
- 任一接口失败都有可见提示和重试入口。
- 同一订单无法并发触发支付、取消、交付或仲裁。
- 页面切换后不会出现旧响应覆盖新数据。

### FE-002 阶段二风控案件工作台缺失

**现状**

后端已有风控案件、处置命令和案件查询接口，但前端交易工作台没有风控案件入口。阶段二能力主要停留在接口层，运营人员缺少操作界面。

**影响**

风控案件无法在页面中查看、筛选、处置和追踪，阶段二的运营闭环不完整。

**建议方案**

1. 新增“风控案件”工作台：
   - 案件列表：状态、风险等级、场景、用户、商家、时间、命中规则。
   - 案件详情：事件证据、指标快照、规则版本、处置命令。
   - 操作区：人工复核通过、驳回、升级、加入名单等。
   - 历史记录：每次操作人、时间、理由、命令状态。
2. 支持状态、等级、场景、时间范围、用户 ID、商家 ID 筛选。
3. 高风险操作必须填写原因并二次确认。
4. 命令失败时提供重试和人工处理入口。

**验收标准**

- 运营人员可以在前端完成案件查询、查看证据、执行处置、追踪命令状态。
- 所有人工操作都有操作原因和审计记录。
- 命令失败可以被看见并进入处理流程。

### FE-003 页面细节与用户引导不足

**现状**

- 订单、托管、售后、提现等状态存在英文枚举直出。
- 管理员点击“查看证据”后，`selectedDispute` 被赋值，但当前渲染结构中未看到证据详情展示。
- 卡密明文直接展示，缺少一次性披露提示和复制体验。
- 评价固定 5 星和固定文案，售后原因固定。
- 金额、价格等输入只判断非空，缺少数字范围和格式校验。
- 全额退款、全额放款、打款等资金操作缺少强制确认。

**影响**

用户难以理解业务状态；关键证据没有形成决策链路；误操作资金类按钮的风险较高。

**建议方案**

1. 建立统一状态字典，将后端枚举映射为中文文案、颜色和说明。
2. 仲裁前必须先查看证据，证据面板展示文件、内容、上传人和时间。
3. 卡密查看改为显式披露：
   - 默认脱敏。
   - 点击“查看明文”后提示安全风险。
   - 提供复制按钮和查看审计提示。
4. 评价和售后改为真实表单，支持星级选择、原因选择和补充说明。
5. 金额、价格、数量使用统一数值校验：
   - 必须是数字。
   - 大于 0。
   - 限制小数位和最大值。
6. 资金类操作使用确认弹窗，展示金额、订单号和影响。

**验收标准**

- 页面不再直接显示英文枚举。
- 仲裁操作必须经过证据查看和确认。
- 卡密默认脱敏，查看明文有风险提示和审计提示。
- 非法输入无法提交。
- 资金操作有二次确认和结果反馈。

## 十一、P2：工程规范与可维护性

### ENG-001 代码组织与基础规范

**现状**

- 订单、资产、资金、风控中大量使用字符串状态，例如 `WAIT_PAY`、`FROZEN`、`ARBITRATING`、`MANUAL_REVIEW`。
- `TradeOrderService` 承担过多职责，依赖较多，方法数量和行数偏大。
- 多处使用 `@Value` 注入零散配置。
- 多处直接 `LocalDateTime.now()`。
- 仍有 `System.out.println` 和 `printStackTrace`。

**建议方案**

1. 为状态、事件类型、操作类型建立枚举或常量类，统一前后端字典。
2. 使用不可变 `@ConfigurationProperties` 组织配置。
3. 注入 `Clock` 替代直接 `LocalDateTime.now()`，方便测试时间边界。
4. 使用 SLF4J 结构化日志，统一 traceId、orderNo、eventNo 字段。
5. 提取业务编号生成、签名工具、JSON 序列化等基础组件。
6. 每个服务保持单一职责，编排类只负责流程，不混合查询和细节规则。

**验收标准**

- 核心状态不再散落魔法字符串。
- 配置可集中校验和打印安全脱敏后的值。
- 时间相关测试可以注入固定 Clock。
- 生产代码没有 `System.out.println` 和 `printStackTrace`。

## 十二、测试与验收建议

### TEST-001 质量保障缺口

已有测试覆盖了支付回调、结算、超时、仲裁、资产预留、提现、风控命令等核心场景，基础是好的。建议补充以下测试：

1. **支付安全**
   - 伪造签名拒绝。
   - nonce 重放拒绝。
   - 时间窗口校验。
   - 并发回调只成功一次。
2. **跨服务一致性**
   - 远程成功、本地回滚后的补偿。
   - MQ 重复消费。
   - 命令超时自动恢复。
3. **性能与并发**
   - 卡密批量导入基准。
   - 并发锁定无超卖。
   - 风控评估查询次数上限。
   - 大列表分页性能。
4. **规则一致性**
   - 多实例规则缓存刷新。
   - 规则版本进入决策证据。
5. **接口契约**
   - 参数校验。
   - 错误码和 HTTP 状态。
   - 权限边界。
6. **前端关键路径**
   - 下单、支付、交付、确认、结算。
   - 发起售后、查看证据、仲裁。
   - 风控案件查询和处置。
   - 弱网、接口失败、重复点击。

**验收标准**

- P0 问题修复必须伴随回归测试和安全测试。
- P1 性能优化必须给出优化前后的基准数据。
- 前端关键路径至少有自动化冒烟或 E2E 测试。
- 多实例场景有并发和重复消费测试。

## 十三、推荐实施顺序

### 第一批：安全与一致性

1. 修复支付回调签名、时间戳、nonce 和重放防护。
2. 梳理跨服务操作清单，为每一步补充幂等键和补偿定义。
3. 将远程调用移出长事务。
4. 增加支付安全和对账测试。

### 第二批：查询与性能

1. 统一分页 DTO、筛选条件和总数返回。
2. 批量化卡密导入和锁定。
3. 落地风控指标物化。
4. 优化关系图谱查询。
5. 为慢查询和评估耗时建立监控。

### 第三批：运营闭环

1. 增加风控案件工作台。
2. 完善证据展示、资金操作确认和状态字典。
3. 补充加载、错误、重试和并发控制。
4. 补充命令失败处理入口。

### 第四批：工程规范

1. 状态枚举和配置类治理。
2. 拆分订单编排服务。
3. 统一异常、日志、traceId 和错误码。
4. 清理测试接口的生产暴露风险。

## 十四、评审结论

阶段一和阶段二的业务骨架已经比较完整，Schema、幂等键、状态流转和部分补偿逻辑都有基础。当前不建议做大规模推倒重构，而是先补齐安全边界和一致性模型，再解决查询与风控性能，最后把运营工作台和前端体验补完整。

最优先的三件事是：

1. 重构支付回调签名与防重放机制。
2. 建立跨服务操作意图、幂等键和自动补偿。
3. 为列表和风控指标建立分页与物化方案。

完成这三项后，系统再进入更大规模的联调和压测会更有把握。
